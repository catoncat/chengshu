# 造物桌：体验剧本与动效分镜

> 配套 [设计方向](README.md) 与 [可操作原型](prototype.html)。本文讨论“人看到什么、怎么操作、发生什么”，不规定插件 API 或实现架构。
> 分清三层：本轮原型有的交互；建议正式产品采用的规则；尚未做出的探索效果。具体交付边界见 [VALIDATION.md](VALIDATION.md)。

## 1. 第一眼不是一片空白画布

### 已从系统分享带入内容

画面先出现一张带真实缩略图/标题的原料卡，下方是三张适合它的成品配方。“做成阅读版”“放进笔记”“复制文字”。主推荐完整露出，其余不靠扇形重叠藏名称。

主配方一键运行。旁边的“展开改一改”才进入桌面。用户赶时间时，整个卡牌世界都可以不出现。

### 从桌面图标打开

默认进入口袋：常用配方、最近成果、需要接续的事情。没有配方时，三张起手配方和“用示例试一下”，不要求先逛商店安装模组。

本轮原型为了评审设计，默认进入造物桌。不能把这一演示默认当成正式产品日常首页的决定。

## 2. 卡牌语法：规则应该长在卡上

### 三种角色，不是三种固定位置

**输入卡：** 我现在有什么。例：网页、文字、照片、声音、文件。上方写来源，下方写拿到的内容。带样例或缩略图，而不是只有抽象图标。

**能力卡：** 我希望它怎样变化。例：整理正文、识字、转成文字、翻译、整理清单。卡底明确“图片 → 文字”。能力可以零张，也可以串联多张。

**去向卡：** 我要把结果放哪里。例：阅读器、笔记本、剪贴板、文件、待办。卡面首先写用户目的，格式是次级说明。“阅读器”可以在卡内完成必要的成书处理，不强迫用户额外摆一张 EPUB 卡。

同一模组可以提供多张卡，也可以让一个能力在不同场景承担不同角色。不要在视觉上把“插件包”“卡牌”“配方”都叫同一种东西。

### 卡正面只回答四件事

1. 它做什么：大标题，例如“整理清单”。
2. 它接什么、产生什么：短标签，例如“文字 → 待办”。
3. 它用在哪里：一行样例，例如“把会议里的承诺整理出来”。
4. 有没有需要提前知道的代价：联网、付费、写入/公开发布等，用文字而非隐晦图标。

作者、版本、依赖、细设置放在详情，但会改变数据去向的东西不得只藏在卡背。模组皮肤不得覆盖这些固定区域。

### 形状也是语法

输入卡的末端有“给出”标记；能力卡两端都有；去向卡终止路径。文字、图片、声音、文件采用可辨识的小图形并配文字。颜色只是辅助，不承担唯一语义。

卡面编号是识别符，不是等级。不要给下载量大的作者金边，让人误以为更安全。不要把不能连接的卡画成“你等级不够”。

## 3. 接牌：解释可能性，不惩罚试错

点“加一张”后，抽屉默认展示当前能接的能力；用户也能查看全部。不能接的卡仍可了解，旁边写出原因。

例：当前是一张截图，“翻成英文”需要文字。提示不是“类型不匹配”，而是：

> 这张卡要先拿到文字。加入“识字”，就能继续。

用户明确点击后才补上缺的一步；给出撤销。不能因为系统判断可以“聪明修复”，就悄悄更换三个模组、改成收费联网路径。

替换卡时，预览后续影响。例如“换成原图保存后，这两步将不再适用”。保留配方草稿，不因一次错误尝试清空桌面。

**原型已实现：** 点选加入/更换、兼容检查、原因提示、显式修复、前移/后移、移除、撤销。原型的修复是有限示例规则，不是智能推荐引擎。

**后续效果提案：** 长按拿起、合法槽位磁吸、拖动占位、放下后轻回弹。全部必须保留等价的点选操作。复杂动作不要求手指精确拖到两毫米端口上。

## 4. 一次完整的创造旅程

### 分镜 01：先给一份具体的东西

输入：“周末小计划”的截图。

原料卡露出标题和几行缩略文字。桌上不是一排空框；下一步只问“你想把它变成什么？”手牌里优先出现“识字”，其他选择仍能找。

### 分镜 02：把能力放上去

点“识字”，新卡在输入后落下，后方出现一张薄薄的文字预览。不是先执行昂贵真实任务，只用样例说明作用；真实处理与预览的区别明确标注。

卡口闭合后，配方摘要从“图片”变成“把图片里的文字……”。界面的语言随着组合成长。

### 分镜 03：给成果找去处

加上“笔记本”。配方现在读成“把截图里的文字存进笔记”。主按钮可执行。

首次涉及真实外部写入时，确认具体账户/位置；没有连接时保留配方，用示例试跑，并提供“连接此去向”。卡库里看见一个应用不等于已经获得写入权限。

### 分镜 04：看见作用，而不是看一次烟花

原料的身份保持连续，依次强调正在工作的那张卡。下方出现文字，再变成笔记预览。已经完成的阶段留下可查看的结果。

完成后主角是新笔记，不是一个巨大的绿色对勾。用户立刻能打开、复制、保存或继续接别的卡。

### 分镜 05：收好这套办法

按钮“收进口袋”。默认命名“截图变笔记”，用户可以改。几张卡收成一张封套卡，飞向口袋入口。

下次分享截图，口袋卡直接可用。不要让用户为了同一个动作反复搭同一套牌。

本轮原型用一张短暂的“配方封套”向口袋移动来表达收纳；没有完整三维折叠或每张卡的共享元素变形。那是后续动效细化，不宣称已经实现。

## 5. 日常与创造之间要能无缝往返

一张收藏配方既是快捷方式，也是可展开的说明书。正常点主按钮使用；点“展开改一改”看到内部步骤。

改编别人配方时生成自己的副本，不修改原作品。保存时可以选择覆盖自己的旧版本或另存，不能默认改掉所有历史运行的含义。

“最近成果”和“我的配方”是不同东西：前者是某次做出的文件/内容，后者是可复用的做法。视觉上成果像一张有标题/时间的小票，配方像封套卡。不让用户误以为删配方就会删结果。

本轮原型：口袋保存配方；运行成果只在当前页面演示，刷新不会恢复运行。没有实现真正的成果库与系统分享入口，不能据此宣传可靠后台执行。

## 6. 更通用的组合，不变成一团电线

### 零加工

文字 → 剪贴板；图片 → 保存文件。直接连接就是完整配方，不显示“缺少处理步骤”。原型可通过“新配方”验证。

### 多加工

录音 → 转成文字 → 整理清单 → 笔记。桌面上每一步可查看和移动。移动到错误位置时保留它并解释原因，不直接执行错误流程。

超过四五步后，正式产品允许把一段收成组合卡，卡面写“内含 4 步”，点开在独立层编辑。不要让用户无限横向拖动寻找终点。本轮原型上限为六张中间能力卡；没有实现嵌套组合。

### 多输出

同一份文字同时去笔记和文件。末端分成两个明确托盘。每个托盘各自显示“准备好了 / 需要处理”，一个失败不会把另一个盖成失败。

默认并行去向不表示顺序执行。如果第二个必须等第一个回传链接才能运行，就应是下一段明确的配方，不用两个并列图形表达有先后依赖的操作。

本轮原型最多两个末端输出，只演示独立结果与单支重试，不包含通用流程图或条件分支。

### 多输入

未来可以把多张图片放进“收件托盘”，先选择“逐个做 / 合在一起”。数量徽标和预览让人知道正在处理几份。不要把“从文件选十张图”偷偷解释成“拼成一个 PDF”。

需要同时结合录音和图片的配方，输入区显示两个具名插槽与缺件状态。仍不要求用户画任意连线。本轮原型未实现多输入；它是下一轮设计验证项。

### 条件与确认

用户先按真实场景选择“没有识别出文字时，只保留图片”。条件藏在相关能力的说明里，复杂规则才展开。初次用户不面对 if/else 菱形。

公开发布、发送消息、付费和改写文件有独立的执行前确认。试配和运行不能被一个炫酷的“合成”手势混为同一件事。

## 7. 失败也有物理连续性

### 不相容：没接上，不是炸了

两张卡之间保留一小段间隙与可读原因；不震屏、不红闪、不让卡跌出视野。不将技术错误渲染成用户“打错牌”。

### 执行失败：停在发生问题的那一张

已完成的原料/正文/成果不消失。失败卡停住，面前保留已经到达它的内容。按钮是“从这里重试”“换张卡”“先保存已有结果”，不是整条流程唯一一个重来。

### 部分成功：两个托盘，两个事实

笔记准备好了，文件去向暂不可用。左托盘正常可用，右托盘解释并可重试。主标题“有一个去处没接通，已有成果还在”。不要写“全部失败”，也不要写“全部完成”。

### 模组缺失/升级不兼容

用可辨识的空卡保留原位置、名称与作者，注明“这张卡目前不可用”。推荐兼容替代，并预览替换后的数据去向与结果。收藏不会因社区作者离开而凭空消失。

权限扩张只暂停受影响的运行。不在模组更新时弹一页英文权限列表要求用户盲目接受。

### 停止

停止有稳定入口；已经执行的外部动作不能靠“撤销动画”假装收回。能撤销的显示撤销，不能撤销的解释已发生的部分。

原型停止仅取消示例计时与后续示例结果；不代表正式任务取消/补偿机制已实现。

## 8. 动效语言：每次运动都要回答一个问题

建议节奏，而非实测性能指标：

| 动作 | 希望用户理解 | 建议时间与运动 | 减少动效时 |
| --- | --- | --- | --- |
| 选中一张卡 | 我拿起了这件东西 | 100–160ms，轻抬 4–6px，不放大整页 | 描边变化 |
| 候选槽位出现 | 这里能放它 | 120–180ms，轮廓显现，不四处闪烁 | 直接显现 |
| 放入并连通 | 规则成立了 | 180–240ms，短位移，最多一次小回弹 | 直接落位 + 状态文字 |
| 不相容 | 这里缺一种内容 | 卡口间隙保持，原因淡入；不左右狂抖 | 原因直接出现 |
| 内容经过某一步 | 现在正在做这件事 | 只强调活动卡，持续由真实工作驱动 | 状态文字 + 静态高亮 |
| 形成结果 | 新东西已经可用 | 180–260ms，成果出现，保持来源可见 | 直接显示成果 |
| 收成配方 | 做法被保存，可下次再用 | 350–550ms，卡叠变封套，进入口袋 | 直接加入并播报 |
| 展开配方 | 我要改内部的一部分 | 220–320ms，相关卡展开；其他区域不大幅飞动 | 直接展开 |
| 只重试一个去向 | 其他东西不再处理 | 仅那一支反馈，不重播全流程 | 局部状态更新 |

不做全页粒子、不做每次两秒开场、不让按钮等待动画结束才响应、不用动画时长伪装任务百分比。常用动作可更短，首次教学可稍完整。

声音默认关闭。后续可选轻触觉只用于落位/完成/需要确认，不能依赖震动传达错误；不在每张卡经过时震一下。原型没有声音与震动。

动效是连续性的解释，不是掩盖等待的烟幕。

## 9. 手机不是桌面缩小版

手机上，阅读方向从左到右改为从上到下。卡面变宽、缩略图变小、细设置收进抽屉，卡的角色与连接语法不变。

主操作在拇指可达的底部操作条；页面留出空间，不能遮挡最后一行。底部条只在造物桌出现，切口袋/工坊不残留无关按钮。

多输出变成两个向右缩进的托盘，不把用户推到横向迷宫里。长配方以“当前步骤 + 后续摘要”逐层展开；本轮原型为可滚动纵向全展开，用于检查规则与布局，尚未实现复杂配方折叠。

拖动是可选玩法。按钮前移/后移、加入/移除必须完整可用。手机不能用 hover 才显示主操作，也不能强迫长按才发现菜单。

正文状态用文字说明，不只靠薄荷/橙色区分。大字体不把标题缩小成卡牌游戏的小字。屏幕阅读器读出“输入，一张截图，给出图片；下一步识字，图片变文字”，而不是“节点 0”。

网页无障碍参考：
- W3C [Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)：拖动应有无需拖动的指针替代方式。
- W3C [Animation from Interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)：非必要交互动效应可关闭。

原型支持按钮操作、原生对话框、Escape、可见焦点、系统减少动效与手动减少动效。没有完成真实 TalkBack/VoiceOver 全链验收，不能称已达到某个合规等级。

## 10. 社区工坊：展示玩法，而不是包管理器

作品卡要像一份小型演示：

> “把走路时的想法变成行动清单”
> 原来：一段录音。
> 之后：一份可检查的清单。
> 需要：转写、整理清单、笔记去向。
> 作者：配方作者；每张能力卡另有作者。

作品详情先展示前后样例，接着是可展开的卡组。依赖缺失、版本要求、数据去向和费用在“加入”前可见。真实使用的联网/付费估计必须基于实际能力，不能编一个 0.01 元让界面显得完整。

三种操作必须分开：

**试配：** 使用公开样例，不读取自己的内容、不安装、不授权。

**加入：** 保存配方及所需能力的安装意图，给清楚的依赖与来源摘要。

**运行：** 使用具体输入，对外部写入/发送按风险确认。不是点过一次加入就永久同意任何后续作者升级。

原型实现了虚构作品详情、去向披露、以样例载入可编辑副本；没有真实安装器、社区账号、点赞/下载数或评分。

### 发现机制

先按用途浏览：“读得更舒服”“灵感别丢”“把重复的小事接起来”，再按来源/去向筛选。展示最近可用性、输入输出样例与作者维护状态，比单一热门榜更重要。

空工坊可以用官方起手配方和“把我的配方分享出来”，不伪造繁荣。不要把任务成功次数做成用户必须累积的战力。

### 作者创作体验

先从自己的已跑通配方发布：名称、适用场景、公开样例、效果预览、所需卡、权限与费用说明。发布前提醒样例是否包含私人数据。改编记录来源，允许别人继续改。

卡面插画和主题包可以有个性，但所有主动作、权限、错误与无障碍文字有固定结构。创作者不能用皮肤把“会发送到外部”藏成一个看不见的小点。

## 11. 不该复制的游戏机制

不要消耗卡牌、不要随机抽取功能、不要升级解锁工具、不要失败扣资源、不要强制任务链、不要为了多留用户一分钟而延迟结果。

可以学习的是：有限而清楚的动作、所见即规则、一个物体的连续变化、组合带来的涌现、低风险试验和自己的作品集。

最好的“奖励”就是一份本来要花很久才能弄好的笔记，以及一张下次一秒就能使用的配方。

## 12. 下一轮设计验证，而不是先写插件底座

找 5–8 位从未看过方案的人，给任务，不教术语。样本规模只是形成性可用性研究建议，不能推断市场结论。

| 任务 | 观察问题 | 可据此修改什么 |
| --- | --- | --- |
| 用一篇文章进入阅读器 | 会不会被迫先学摆牌 | 首页与快捷层 |
| 把截图改成笔记 | 是否分得清输入、能力、去向 | 卡面语法与候选抽屉 |
| 加第二个目的地 | 是否误以为两个动作有先后依赖 | 分支结构与文案 |
| 故意放不相容卡 | 能否自行解释缺什么并修复 | 错误提示与修复预览 |
| 保存，下次再用 | 是否认为保存的是文件而非做法 | 配方与成果的视觉区别 |
| 试用社区作品 | 是否以为已经安装/授权 | 试配、加入、运行的分离 |
| 出现部分失败 | 会不会重跑已成功的部分 | 成果托盘与局部重试 |
| 大字体、单手操作 | 是否必须精确拖动或找隐藏操作 | 手机布局与按钮替代 |

先记录首次完成、犹豫点、误操作、对数据去向的理解，不用“用户觉得很好看”代替可用性。若卡牌隐喻拖慢熟练使用，就继续把复杂性收回创造层，不要求用户适应设计师的表演。

## 13. 下一位设计/开发模型接手要求
